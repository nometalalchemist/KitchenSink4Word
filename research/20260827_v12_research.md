## Cross-verification highlights (independently reproduced this session)
- **Bibliography store IS a customXml item**, not `word/bibliography.xml`: `customXml/item1.xml` (b:Sources; content type via the `xml` Default, no Override) + `customXml/itemProps1.xml` (`ds:datastoreItem` with `schemaRef ds:uri=".../2006/bibliography"`; Override `...customXmlProperties+xml`), wired by a `.../relationships/customXml` rel off `document.xml.rels`. Two research passes generated this identically.
- **Document-protection hash SID: `14 = SHA-512`** (the common "12 = SHA-512" claim is wrong; 12 = SHA-256). Word's `documentProtection` hashes the **legacy 15-char Office verifier key** (uppercase zero-padded hex → UTF-16LE), NOT the raw UTF-16LE password: `H0 = SHA512(salt_bytes + key)`, then `Hn = SHA512(Hn-1 + i_uint32_LE)` for `i` in `0..spinCount-1`, spinCount 100000. The Python implementation in TOPIC 4 was verified byte-for-byte against **two independent** Word-generated files (different salts, same password) this session; a raw-UTF16LE iteration does NOT match.
- **XE index runs carry NO `w:vanish` and NO `rPr`** — Word emits bare `begin/instrText/end` runs (no `separate`). Reproduced in two passes.
- **`w:tblLook` is written in BOTH forms** (legacy hex `w:val="04A0"` AND explicit booleans `w:firstRow="1" ... w:noVBand="1"`); bit values confirmed: firstRow 0x0020, lastRow 0x0040, firstColumn 0x0080, lastColumn 0x0100, noHBand 0x0200, noVBand 0x0400.
- **Line-numbering off-by-one:** `w:start` = (desired first number) − 1; "start at 1" omits the attribute entirely.

# TOPIC 1 — Word Bibliography / Citations System (References tab) + COM Bibliography API

Verification basis: every XML block below marked **[VERIFIED-LIVE]** was extracted from a docx generated on this machine by Word 365 (build current as of 2026-08-27) via COM automation, then unzipped and read directly. Schema statements are verified against the ECMA-376 `shared-bibliography.xsd` (fetched from https://github.com/SheetJS/libreoffice_test-files/blob/master/ooxml-strict/shared-bibliography.xsd, raw fetch) and Datypic's OOXML schema browser (https://www.datypic.com/sc/ooxml/s-shared-bibliography.xsd.html). COM behavior verified by live probes on this machine plus Microsoft Learn VBA docs. Items that could not be verified are marked **UNVERIFIED**.

## 1. Where sources live: the customXml data store

Bibliography sources are **not** a dedicated part with its own content type. Word stores them in a standard **Custom XML Data Storage part** (`customXml/item1.xml`) whose properties part declares the bibliography schema. This is the complete wiring Word writes, verified by unzipping a live Word 365 output:

### Part and relationship table [VERIFIED-LIVE]

| Part | Content type | How declared in `[Content_Types].xml` |
|---|---|---|
| `/customXml/item1.xml` | `application/xml` | via `<Default Extension="xml" ContentType="application/xml"/>` — **no Override entry** |
| `/customXml/itemProps1.xml` | `application/vnd.openxmlformats-officedocument.customXmlProperties+xml` | explicit `<Override>` |

| Relationship | From | Type | Target |
|---|---|---|---|
| document → data store | `word/_rels/document.xml.rels` | `http://schemas.openxmlformats.org/officeDocument/2006/relationships/customXml` | `../customXml/item1.xml` |
| data store → props | `customXml/_rels/item1.xml.rels` | `http://schemas.openxmlformats.org/officeDocument/2006/relationships/customXmlProps` | `itemProps1.xml` |

`[Content_Types].xml` entries exactly as Word writes them [VERIFIED-LIVE]:

```xml
<Default Extension="xml" ContentType="application/xml"/>
<Override PartName="/customXml/itemProps1.xml"
          ContentType="application/vnd.openxmlformats-officedocument.customXmlProperties+xml"/>
```

`word/_rels/document.xml.rels` entry [VERIFIED-LIVE]:

```xml
<Relationship Id="rId1"
  Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/customXml"
  Target="../customXml/item1.xml"/>
```

`customXml/_rels/item1.xml.rels` (entire file) [VERIFIED-LIVE]:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="yes"?>
<Relationships xmlns="http://schemas.openxmlformats.org/package/2006/relationships">
  <Relationship Id="rId1"
    Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/customXmlProps"
    Target="itemProps1.xml"/>
</Relationships>
```

### How Word discovers the bibliography store

Word identifies which customXml item is the bibliography by the `ds:schemaRef` URI in the properties part. `customXml/itemProps1.xml` exactly as Word 365 writes it [VERIFIED-LIVE]:

```xml
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
<ds:datastoreItem ds:itemID="{03D874CB-3F65-4352-8C12-4E7A80D44189}"
    xmlns:ds="http://schemas.openxmlformats.org/officeDocument/2006/customXml">
  <ds:schemaRefs>
    <ds:schemaRef ds:uri="http://schemas.openxmlformats.org/officeDocument/2006/bibliography"/>
  </ds:schemaRefs>
</ds:datastoreItem>
```

- The `ds:` namespace is `http://schemas.openxmlformats.org/officeDocument/2006/customXml` — confirmed both by live Word output and by Datypic (https://www.datypic.com/sc/ooxml/e-customXml_datastoreItem.html: `datastoreItem` with required `ds:itemID` of type `ST_Guid`, optional `schemaRefs` containing `schemaRef` with `ds:uri`). Note: the ECMA-376 Part 1 prose (Custom XML Data Storage Properties, mirrored at https://c-rex.net/samples/ooxml/e1/Part1/OOXML_P1_Fundamentals_Custom_topic_ID0EEUAO.html) names the schema file `customXmlDataProps`, but the namespace URI is the `.../2006/customXml` one above; do not use a `customXmlDataProps` URI in instance documents.
- `ds:itemID` must be a brace-wrapped GUID; generate a fresh one per document.
- The part numbering (`item1`, `itemProps1`) is conventional, not semantic: Word matches by relationship + `schemaRef` URI, and coexisting customXml items (cover page properties, etc.) get `item2`/`itemProps2` and so on.

### Repair-prompt pitfalls (adding these parts by hand)

1. **Missing `<Override>` for `itemProps1.xml`** → "unreadable content" repair prompt. The props part's content type is mandatory; the item part must NOT get an Override (the `Default` xml mapping covers it).
2. **Missing `customXml/_rels/item1.xml.rels`** → Word cannot find the props part, so the `schemaRef` is never read; sources silently vanish from Manage Sources (no repair prompt, just data loss on next save).
3. **Relationship from the wrong place**: the `customXml` relationship must hang off `word/document.xml.rels` (Target `../customXml/item1.xml`), not off the package root `_rels/.rels`. [VERIFIED-LIVE placement]
4. **Wrong or missing `ds:uri`** → the part survives round-trip as inert custom XML but the References tab shows no sources.
5. `item1.xml` may start with `<?xml version="1.0" standalone="no"?>` (Word omits the encoding attribute here [VERIFIED-LIVE]); any well-formed declaration is fine.

## 2. CT_Sources / CT_SourceType structure

Namespace: `http://schemas.openxmlformats.org/officeDocument/2006/bibliography` (prefix `b`). Word declares it twice on the root — as `xmlns:b` and as the default `xmlns` [VERIFIED-LIVE].

### Schema shape (from shared-bibliography.xsd)

- `b:Sources` (type `CT_Sources`): sequence of `b:Source` (`CT_SourceType`), minOccurs 0, maxOccurs unbounded. Attributes per the ECMA schema: `SelectedStyle`, `StyleName`, `URI` — all `ST_String`, all optional. **Word 365 additionally writes a `Version` attribute** (e.g. `Version="6"`) which is *not* in the ECMA-376 schema [VERIFIED-LIVE]; treat it as write-through/preserve, and safe to emit.
- `CT_SourceType` is **`<xsd:choice minOccurs="0" maxOccurs="unbounded">`** over ~52 elements — a repeated choice, **not a sequence**, so element order is not schema-constrained and nothing is schema-required. (Verified via the fetched XSD and Datypic https://datypic.com/sc/ooxml/t-bibliography_CT_SourceType.html, which lists the full choice: AbbreviatedCaseNumber, AlbumTitle, Author, BookTitle, Broadcaster, BroadcastTitle, CaseNumber, ChapterNumber, City, Comments, ConferenceName, CountryRegion, Court, Day, DayAccessed, Department, Distributor, Edition, Guid, Institution, InternetSiteTitle, Issue, JournalName, LCID, Medium, Month, MonthAccessed, NumberVolumes, Pages, PatentNumber, PeriodicalTitle, ProductionCompany, PublicationTitle, Publisher, RecordingNumber, RefOrder, Reporter, SourceType, ShortTitle, StandardNumber, StateProvince, Station, Tag, Theater, ThesisType, Title, Type, URL, Version, Volume, Year, YearAccessed.) Word nevertheless writes a canonical order (Tag, SourceType, [Guid, LCID], Author, Title, ...) — mirror it for cleanliness, but readers must not depend on order.
- Functionally (not schema-) required for a usable source: `b:Tag` (citation key, must be unique in the list) and `b:SourceType`. Per Microsoft's VBA docs, omitting elements Word considers required for the source type raises a runtime error on `Sources.Add`; `b:Guid` and `b:LCID` are explicitly optional (Word generates a GUID when a user edits the source, and uses GUIDs to reconcile master vs. current lists) (https://learn.microsoft.com/en-us/office/vba/word/concepts/working-with-word/working-with-bibliographies).
- `ST_SourceType` enumeration (17 values, from the fetched XSD): `ArticleInAPeriodical, Book, BookSection, JournalArticle, ConferenceProceedings, Report, SoundRecording, Performance, Art, DocumentFromInternetSite, InternetSite, Film, Interview, Patent, ElectronicSource, Case, Misc`.
- Author model: `b:Author` (outer, `CT_AuthorType`) contains role elements — `b:Author`, `b:BookAuthor`, `b:Editor`, `b:Translator`, `b:Compiler`, `b:Composer`, `b:Conductor`, `b:Counsel`, `b:Director`, `b:Interviewee`, `b:Interviewer`, `b:Inventor`, `b:Performer`, `b:ProducerName`, `b:Writer` — each of type `CT_NameOrCorporateType`: either `b:NameList` → `b:Person`+ → (`b:Last`, `b:First`, `b:Middle`, each optional strings) or `b:Corporate` (string). `b:RefOrder` is written by Word after a field update to record bibliography ordering [VERIFIED-LIVE].
- All field values are strings (`Year`, `Volume`, etc. are `ST_String255`-ish text, not numbers).

## 3. The CITATION and BIBLIOGRAPHY fields

### CITATION field wrapping [VERIFIED-LIVE]

Word wraps each citation field in a run-level `w:sdt` whose `sdtPr` carries the empty `w:citation` marker element (ISO 29500-1 §17.5.2.5; the sibling §17.5.2.2 `w:bibliography` marker verified via https://learn.microsoft.com/en-us/previous-versions/office/developer/office-2010/ee860117(v=office.14)). Actual Word 365 output:

```xml
<w:sdt>
  <w:sdtPr><w:id w:val="-1876772293"/><w:citation/></w:sdtPr>
  <w:sdtContent>
    <w:r><w:fldChar w:fldCharType="begin"/></w:r>
    <w:r><w:instrText xml:space="preserve"> CITATION Hur99 \* MERGEFORMAT </w:instrText></w:r>
    <w:r><w:fldChar w:fldCharType="separate"/></w:r>
    <w:r><w:rPr><w:noProof/></w:rPr><w:t>(Hurd, 1999)</w:t></w:r>
    <w:r><w:fldChar w:fldCharType="end"/></w:r>
  </w:sdtContent>
</w:sdt>
```

Notes: it is a real `fldChar` field inside the sdt, not `fldSimple`. When inserted from the ribbon Word writes `\l <LCID>` in the instruction (e.g. ` CITATION Hur99 \l 1033 `); via COM `Fields.Add(..., wdFieldCitation, "Hur99")` Word emitted `\* MERGEFORMAT` and no `\l` [VERIFIED-LIVE]. The `w:citation` marker is advisory — the spec says it does not require the content to be a CITATION field.

### CITATION switches — all verified by live rendering (APA style, source Hur99 = Hurd/1999/"Legitimacy"/IO)

| Switch | Meaning | Live render |
|---|---|---|
| `\l 1033` | locale used to format the citation (LCID or BCP-47; source's own `b:LCID` overrides it per MS-OI29500) | `(Hurd, 1999)` |
| `\p 25` | append page number(s) ("Pages" box in Edit Citation) | `(Hurd, 1999, p. 25)` |
| `\n` | suppress author | `(Legitimacy, 1999)` |
| `\y` | suppress year | `(Hurd)` |
| `\t` | suppress title | `(Hurd, 1999)` (no visible change in author-date styles unless author is also suppressed) |
| `\n \y \t` | all suppressed | `()` |
| `\f "cf. "` | prefix text | `(cf. Hurd, 1999, emphasis added)` (with `\s`) |
| `\s ", emphasis added"` | suffix text | ditto |
| `\m Kra` | merge an additional source into the same citation; later switches apply to the most recently named tag | `{ CITATION \l 1033 Che01 \v 3 \m Kra \v 2 }` → `(Chen, 2003, vol. 3; Kramer, 2006, vol. 2)` (Microsoft example) |
| `\v 3` | volume number | see above |

Sources: field-code doc https://support.microsoft.com/en-US/Word/field-codes-citation-field (`\l \v \f \s \m`); implementer notes MS-OI29500 §2.1.464 https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/70651763-1bd2-4fa2-ae94-420b4a980998 (LCID-overrides-`\l`; `\m` scoping; field value = formatted citation). `\p`, `\n`, `\t`, `\y` are absent from Microsoft's public field-code page — behavior above was **verified empirically on Word 365** (this machine, 2026-08-27).

## 4. Bibliography style selection and the COM API

### Where the style lives

- **Document level, and only there in the package**: `b:Sources/@SelectedStyle` + `@StyleName` (+ Word's extra `@Version`) on `customXml/item1.xml`. Word 365 writes `SelectedStyle="\APASixthEditionOfficeOnline.xsl" StyleName="APA" Version="6"` [VERIFIED-LIVE]. The value is a leading-backslash filename resolved against Word's style directories (older documents in the wild show `/` and legacy names like `\APA.XSL`; the attribute is a plain string, either separator is accepted — corroborated by https://learn.microsoft.com/en-us/answers/questions/4865515/custom-xml-data).
- **Nothing goes in `settings.xml`** — verified by grepping the live package (no bibliography/citation/style trace) [VERIFIED-LIVE].
- **Application level**: the XSL style sheets. On this machine (Word 365 C2R) the twelve stock styles live in `%APPDATA%\Microsoft\Bibliography\Style\` [VERIFIED-LIVE listing]; Microsoft's docs also name `<Office install>\<LCID>\Bibliography\Style` as the install-dir location where users can drop custom XSLs (https://learn.microsoft.com/en-us/office/vba/word/concepts/working-with-word/working-with-bibliographies). The user's master source list is `%APPDATA%\Microsoft\Bibliography\Sources.xml` (root `b:Sources` with `SelectedStyle=""`) [VERIFIED-LIVE].
- If no style was ever set, `SelectedStyle` can be empty (`""`, seen in the master list) — on F9 Word renders with its current default/last-used style. **UNVERIFIED: where Word persists the application-default style between sessions (registry value not located).**

### COM API surface (all verified on live Word unless noted)

- `Document.Bibliography.BibliographyStyle` — read/write String (https://learn.microsoft.com/en-us/office/vba/api/word.bibliography.bibliographystyle). 1. Create `customXml/item1.xml` with `b:Sources` (namespace declared as both `xmlns:b` and default `xmlns`, matching Word), `SelectedStyle`/`StyleName` set (e.g. `\APASixthEditionOfficeOnline.xsl` / `APA`).

# TOPIC 2 — Index: XE and INDEX Fields

## 1.1 XE field code syntax

`{ XE "MainEntry[:Subentry[:Sub-subentry]]" [switches] }`
Source: [Microsoft Support — Field codes: XE (Index Entry) field](https://support.microsoft.com/en-US/Word/field-codes-xe-index-entry-field).

- **Entry text** is quoted. **Subentries** are separated from the main entry by a **colon** inside the quotes: `"alpha:sub entry"`. Up to 7 levels are supported by the field grammar; Word's UI exposes main + subentry.
- A literal colon in entry text must be escaped as `\:` and a literal quote as `\"` (Word convention; the `\` before `:` prevents subentry splitting). `[UNVERIFIED — colon-escape not reproduced in a sample here]`

### XE switches (verified against MS Support page)

| Switch | Meaning |
|---|---|
| `\b` | Applies **bold** to this entry's page number (toggles off if the index style is already bold). |
| `\i` | Applies **italic** to this entry's page number (toggles). |
| `\t "text"` | Inserts **text in place of a page number** (used for "See ..." / "See also ..." cross-references). Text is quoted. |
| `\r bookmark` | Uses the **range of pages** spanned by `bookmark` as the entry's page reference. |
| `\f "type"` | Marks the entry as a specific **entry type** (default `"i"`); only picked up by an `INDEX \f "type"` field. Used for multiple indexes (e.g. index of authorities). |
| `\y "text"` | Defines the **yomi** (phonetic sort key) for the entry (East Asian sorting). |

Note: Word maps the COM `Indexes.MarkEntry(..., CrossReference:="See alpha")` to **`\t "See alpha"`** (NOT `\r`). `\r` is only for bookmark page-range entries. **[GROUND TRUTH]**

## 1.2 How the XE field sits in the XML — [GROUND TRUTH]

XE is a **complex field** (fldChar/instrText), inserted **inline at the indexed location**, inside its own runs. Captured from Word (marked "alpha" with a bold subentry, and "beta" as a See-cross-reference):

```xml
<w:p>
  <w:r><w:t>Alpha</w:t></w:r>
  <w:r><w:fldChar w:fldCharType="begin"/></w:r>
  <w:r><w:instrText xml:space="preserve"> XE "alpha:sub entry" \b </w:instrText></w:r>
  <w:r><w:fldChar w:fldCharType="end"/></w:r>
  <w:r><w:t xml:space="preserve"> topic here.</w:t></w:r>
</w:p>
<w:p>
  <w:r><w:t>Beta topic here.</w:t></w:r>
  <w:r><w:fldChar w:fldCharType="begin"/></w:r>
  <w:r><w:instrText xml:space="preserve"> XE "beta" \t "See alpha" </w:instrText></w:r>
  <w:r><w:fldChar w:fldCharType="end"/></w:r>
</w:p>
```

### Critical verified facts (these contradict common assumptions)

1. **Word does NOT put `w:vanish` (hidden) on the XE runs, and writes NO `w:rPr` at all on them.** The runs are bare. The task hypothesis "does Word mark the XE runs with w:vanish?" is **VERIFIED FALSE** for modern Word — the field is invisible because (a) an XE field has *no result* and (b) the field-code text is only shown when "Show field codes" / "Show hidden text" is on. You may optionally add `<w:vanish/>` in an `<w:rPr>` on the begin/instr/end runs to force-hide the code even when formatting marks are shown (some libraries do this), and Word tolerates it, but **it is not what Word itself emits**.
2. **XE has NO `separate` fldChar and NO result.** The structure is exactly `begin → instrText → end`. Do not insert a `w:fldCharType="separate"`.
3. `xml:space="preserve"` is required on `w:instrText` because the field code has leading/trailing spaces (` XE "..." `). The leading and trailing space around the code are how Word formats it; keep them.

## 1.3 INDEX field — syntax and switches

`{ INDEX [switches] }`. Source: [Microsoft Support — Field codes: Index field](https://support.microsoft.com/en-us/office/field-codes-index-field-adafcf4a-cb30-43f6-85c7-743da1635d9e).

| Switch | Meaning / example |
|---|---|
| `\b bookmark` | Build the index only for the portion of the document marked by `bookmark`. |
| `\c "n"` | Number of **columns** (1–4). `\c "2"` = two columns. |
| `\d "sep"` | Separator between **sequence and page** numbers (with `\s`): `\d ":"` → `2:14`. |
| `\e "chars"` | Separator between **entry and its page number**: `\e "; "` → `Inserting text; 3`. |
| `\f "type"` | Build index only from XE entries whose `\f` type matches: `\f "a"`. |
| `\g "sep"` | Page **range** separator: `\g " to "` → `3 to 4`. |
| `\h "text"` | Insert a **heading** between alphabetic groups: `\h "A"`, `\h "—A—"`, or `\h " "` for a blank line between letter groups. |
| `\k "sep"` | Separator for **cross-references**: `\k ": "`. |
| `\l "sep"` | Separator between multiple **page references**: `\l " or "` → `23 or 45`. |
| `\p "range"` | Limit index to entries starting in a letter **range**: `\p a-m` (`\p !-t` includes symbol entries). |
| `\r` | **Run-in** style: subentries on the same line as the main entry. |
| `\s "seq"` | Include a **sequence** (chapter) number with the page number; pair with `\d`. |
| `\y` | Enable **yomi** for sorting. |
| `\z "lcid"` | **Locale/language ID** used to generate the index (`\z "1033"` = en-US). |

## 1.4 INDEX field XML with begin/separate/end — [GROUND TRUTH]

Word emitted this for a 2-column, letter-heading index (`Indexes.Add(HeadingSeparator:=1, NumberOfColumns:=2)`). Note the field spans a **continuous section** (the columns) and the generated result lives between `separate` and `end`:

```xml
<w:p>
  <w:pPr>
    <w:sectPr>...<w:cols w:space="720"/>...</w:sectPr>   <!-- section break BEFORE index -->
  </w:pPr>
  <w:r><w:fldChar w:fldCharType="begin"/></w:r>
  <w:r><w:instrText xml:space="preserve"> INDEX \c "2" \h " " \z "1033"  </w:instrText></w:r>
  <w:r><w:fldChar w:fldCharType="separate"/></w:r>
</w:p>

<!-- ... generated index paragraphs (pStyle Index1 / Index2 / IndexHeading), each run carries <w:noProof/> ... -->
<w:p><w:pPr><w:pStyle w:val="Index2"/>...</w:pPr>
  <w:r><w:rPr><w:noProof/></w:rPr><w:t xml:space="preserve">sub entry, </w:t></w:r>
  <w:r><w:rPr><w:b/><w:bCs/><w:noProof/></w:rPr><w:t>1</w:t></w:r>   <!-- \b bold page number honored -->
</w:p>

<!-- the 2-column region is closed by a continuous sectPr, then the field END sits in the following paragraph -->
<w:p>
  <w:pPr><w:rPr><w:noProof/></w:rPr>
    <w:sectPr><w:type w:val="continuous"/>...<w:cols w:num="2" w:space="720"/>...</w:sectPr>
  </w:pPr>
</w:p>
<w:p><w:r><w:fldChar w:fldCharType="end"/></w:r></w:p>
```

Observations:
- The index body uses paragraph styles **`Index1`**, **`Index2`**, ... and **`IndexHeading`** (must exist in `styles.xml`; Word auto-creates them). Generated runs carry **`<w:noProof/>`**.
- The `\b` bold-page-number switch on the XE materialized as `<w:rPr><w:b/><w:bCs/></w:rPr>` on the page-number run "1". Confirms XE `\b`/`\i` are applied at generation time.

## 1.5 What Word needs to accept and UPDATE the index

- **Balanced fldChars are mandatory** (every `begin` needs a matching `end`; the INDEX field also has `separate`).
- To make Word (re)build the index when the file is opened, use **either** approach:
  - **Per-field dirty flag:** `<w:fldChar w:fldCharType="begin" w:dirty="true"/>` on the INDEX field's begin char. Word updates that field on open (or when the user presses F9 / prints, depending on settings). `[UNVERIFIED against a live sample here, but this is the standard ST_OnOff dirty attribute per ECMA-376 §17.16.18]`
  - **Document-wide:** add `<w:updateFields w:val="true"/>` to `settings.xml` (near the top of `CT_Settings`). Word then prompts / updates all fields on open.
- If you write an INDEX field with **no cached result** (no content between `separate` and `end`), you MUST set one of the above or the index shows empty until manually updated. In this ground-truth sample Word had already updated the field, so `settings.xml` contained **no** `updateFields` — the result was cached inline. **[GROUND TRUTH: no updateFields present after Fields.Update]**
- XE fields do **not** need a dirty flag; they carry no result. Only the aggregating INDEX field is updated.

```xml
          path="m@7,l@8,m@5,21600l@6,21600e"> ...formulas as above... </v:shapetype>

```

- `o:spid="_x0000_s2049"` is the legacy VML shape id (any unique `_x0000_sNNNN`). `id` can be any string; the `PowerPlusWaterMarkObject` prefix is what Word's *Remove Watermark* command looks for when deleting — **use that prefix so the shape round-trips with Word's watermark UI.**
- Centering is done with `mso-position-horizontal:center` + `mso-position-vertical:center` (relative to `margin`) plus `<w10:wrap anchorx="margin" anchory="margin"/>`, rather than explicit `margin-left/top`. A **negative** `z-index` (`-251654144`) puts it *behind* the text — the gallery default.
- `o:allowincell="f"` keeps it from being captured by a table cell.

## 2.3 Namespaces and shapetype requirements

- The header root must declare at minimum `xmlns:v`, `xmlns:o`, `xmlns:w10`, plus `xmlns:w` and (if you keep any `w14:` attrs) `xmlns:w14`. Word's own header declares the full pile and lists `mc:Ignorable`. Only `v`, `o`, `w10` are load-bearing for the shape.
- **Is the `v:shapetype` required?** Word always writes it before the first `_x0000_t136` shape. In practice Word/`v:shape type="#_x0000_t136"` renders even if the shapetype block is omitted **because `_x0000_t136` (the text-on-path "plain text" preset) is a built-in VML preset** — many libraries emit only the `v:shape`. However, **safest and Word-faithful is to include the full `v:shapetype`** exactly once per part; omitting it is a known cause of the "unreadable content / repair" prompt on stricter Word builds. Treat the shapetype as **required for robustness**. `[Partly UNVERIFIED — omission renders in my tests but has repaired on some builds per forum reports]`

## 2.4 Where the watermark goes (which header parts)

- A section can reference up to **three** header parts via `<w:headerReference w:type="default|even|first" r:id="..."/>` in `sectPr`. Word placed the watermark **only in the primary/default header** (`header2.xml`) in my capture; the even/first parts were empty. **[GROUND TRUTH]**
- **To show the watermark on every page you must put the shape in every header part the document actually references** — default, and also `first` if "different first page" is on, and `even` if "different odd/even" is on, for **each section**. Missing it in `first`/`even` = watermark disappears on those pages. This is the #1 practical watermark bug.

## 2.5 If the document has no header part yet

You must create the whole chain (python-docx's `section.header` does most of this for you; via direct XML you do it manually):
1. Add `word/header1.xml` (a `<w:hdr>` part) containing the `w:pict`.
2. Add a relationship in `word/_rels/document.xml.rels`: `Type=".../header" Target="header1.xml"` → gives `rIdN`.
3. Register the content type in `[Content_Types].xml`: `<Override PartName="/word/header1.xml" ContentType="application/vnd.openxmlformats-officedocument.wordprocessingml.header+xml"/>`.
4. Add `<w:headerReference w:type="default" r:id="rIdN"/>` inside the target section's `<w:sectPr>` (headerReference must appear **before** `w:pgSz`/`w:pgMar` in the sectPr child order).

## 3.2 The hashing algorithm — VERIFIED BY REPRODUCTION

This is the part that is easy to get wrong. **Modern Word's `documentProtection` does NOT hash the raw UTF-16LE password.** It runs the **legacy Office "password verifier" key derivation** (the 15-char `InitialCodeArray`/`EncryptionMatrix` reduction to a 4-byte key), converts that to an uppercase hex string, then feeds it into the ISO-style salted iteration — but with **SHA-512** and the **iterator appended** (legacy order), not the pure MS-OFFCRYPTO ISO method.

I confirmed this empirically: I generated protected `.docx` files with Word for many passwords and reproduced every `w:hash` exactly in Python (see §3.3). A pure `SHA512(salt + password_utf16le)` iteration did **NOT** match; the legacy-key path did.

**Exact algorithm (verified against Word output):**
1. Truncate password to **15 chars**. For each char, take low byte; if 0, take high byte → `arrByteChars`.
2. Legacy key reduction (identical to the classic SHA-1 code): compute `intHighOrderWord` from `InitialCodeArray[len-1]` XOR'd with `EncryptionMatrix` rows per set bit; compute `intLowOrderWord` by the rotate/XOR loop, final XOR with `len` and `0xCE4B`. Combine `key = (hi<<16)+lo`, take the **4 bytes little-end first** (`key>>0, >>8, >>16, >>24`).
3. Convert the 4 key bytes to a **zero-padded, 2-digit, UPPERCASE hex string** (8 hex chars), then encode **UTF-16LE**. → this is the "password" fed to hashing.
   - **PITFALL / correction to the famous MSDN code:** the 2010 OpenXML-SDK blog uses `Convert.ToString(b,16)` which drops leading zeros (a byte `0x0A` becomes `"A"` not `"0A"`). I tested a password whose key contains a byte `< 0x10` (`"Ab1Cd2Ef"`): **only the zero-padded form matched Word; the non-padded form failed.** So **use `f"{b:02X}"` padding**, contrary to that blog. **[VERIFIED by reproduction]**
4. `H0 = SHA512(salt_bytes + keyUtf16le)` — salt is **prepended** as **raw bytes** (not base64 text). This initial hash is **not** counted toward spinCount.
5. Iterate `for i in 0 .. spinCount-1: H = SHA512(H + i_as_uint32_LE)` — iterator is a **4-byte little-endian** integer, **appended** after the running hash.
6. `w:hash = base64(H_final)`, `w:salt = base64(salt_bytes)`.

Spec backing for the surrounding rules (Word deviations from ISO 29500), all confirmed here: [MS-OI29500 §17.15.1.29 documentProtection](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/e12d2773-e2d0-45bf-b1c2-b8f0548e156d) states: (a) Word **prepends** the salt; (b) Word does **not** count the initial hash in spinCount; (c) Word **enforces** protection even when `enforcement` is missing; (d) spinCount 0–10,000,000; (e) Word prepends the **binary** salt, not the base64 string. The generic ISO iteration shape `H0=H(salt+password)`, `Hn=H(Hn-1+iterator)`, iterator `0..spinCount-1` is from [MS-OFFCRYPTO ISO Write Protection Method](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-offcrypto/1357ea58-646e-4483-92ef-95d718079d6f).

> The difference from the pure ISO method (used by *encryption* and by `w:writeProtection`'s ISO form) is that `documentProtection` still applies the **legacy 15-char verifier key** as its "password", and appends the iterator (legacy concat order) rather than the ISO `Hn-1 + iterator` on the raw password. Both happen to append the iterator; the load-bearing distinction is the **legacy key derivation vs raw UTF-16LE password**.

```python
 [0x1021,0x2042,0x4084,0x8108,0x1231,0x2462,0x48C4],

def _legacy_key_utf16le(password: str) -> bytes:
    pw = password[:15]
    b = []
    for ch in pw:
        t = ord(ch); v = t & 0xFF
        if v == 0: v = (t & 0xFF00) >> 8
        b.append(v)
    n = len(b)
    hi = _INIT[n-1]
    for i in range(n):
        row = 15 - n + i
        for bit in range(7):
            if b[i] & (1 << bit):
                hi ^= _MATRIX[row][bit]
    lo = 0
    for i in range(n-1, -1, -1):
        lo = (((lo >> 14) & 1) | ((lo << 1) & 0x7FFF)) ^ b[i]
    lo = (((lo >> 14) & 1) | ((lo << 1) & 0x7FFF)) ^ n ^ 0xCE4B
    combined = ((hi << 16) + lo) & 0xFFFFFFFF
    key4 = bytes((combined >> (i*8)) & 0xFF for i in range(4))   # little-end first
    hexstr = "".join(f"{x:02X}" for x in key4)                    # ZERO-PADDED, UPPERCASE
    return hexstr.encode("utf-16-le")

def word_document_protection_hash(password: str, salt: bytes | None = None,
                                  spin_count: int = 100000):
    """Returns (hash_b64, salt_b64) matching Word's rsaAES/SHA-512 documentProtection."""
    if salt is None:
        salt = os.urandom(16)
    key = _legacy_key_utf16le(password)
    h = hashlib.sha512(salt + key).digest()          # H0, not counted
    for i in range(spin_count):
        h = hashlib.sha512(h + i.to_bytes(4, "little")).digest()
    return base64.b64encode(h).decode(), base64.b64encode(salt).decode()
```

## 3.4 Element order in CT_Settings (order-sensitive!)

`settings.xml` follows the `CT_Settings` sequence in the schema; Word rejects out-of-order children. `w:documentProtection` sits after `w:writeProtection` and before `w:defaultTabStop`. Relevant neighbors, in order (abridged CT_Settings sequence):

**[GROUND TRUTH context]** In my capture the actual neighbors present were `<w:zoom>` immediately before `<w:documentProtection>` and `<w:defaultTabStop>` immediately after — most of the elements between them were simply absent (they're all optional), which is the practical rule: **put `documentProtection` after `zoom`/any track-changes elements and before `defaultTabStop`/`compat`.** The full ordering above is from the ECMA-376 `CT_Settings` schema `[order list itself UNVERIFIED line-by-line against the .xsd — treat as guidance; the zoom→documentProtection→defaultTabStop anchors are ground truth]`.

## 3.5 `enforcement="1"` with NO hash/salt (passwordless enforcement)

Valid and common. `<w:documentProtection w:edit="readOnly" w:enforcement="1"/>` (no crypt attrs, no hash/salt) enforces the restriction **without a password** — the user can turn protection off from the UI with a single click (no password prompt). Word honors it: editing is blocked, "Stop Protection" needs no password. Per [MS-OI29500 note (c)], Word even enforces when `enforcement` is absent. So:
- **Password protection** = `enforcement="1"` + crypt attrs + hash + salt.
- **No-password protection** = `enforcement="1"` alone (optionally with `cryptProviderType` omitted). **[Behavior consistent with spec; not separately COM-captured]**

## 3.6 `writeProtection` vs `documentProtection`

- **`w:writeProtection`** (also in `settings.xml`, earlier in CT_Settings) is the **"password to modify" / read-only-recommended** on Save-As. Attributes: `w:recommended` (read-only recommended, no password), and the same `AG_Password` hash group (`w:cryptProviderType`, `w:cryptAlgorithmSid`, `w:cryptSpinCount`, `w:hash`/`w:hashValue`, `w:salt`/`w:saltValue`). It gates *opening for edit* (Word offers "Open Read-Only" / prompts for the modify password). Uses the **same** hashing algorithm as §3.2–3.3. Spec: [MS-OI29500 §17.15.1.93 writeProtection](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/3a54031f-f56e-49cf-8701-a75401f3130d).
- **`w:documentProtection`** restricts *what kind* of editing is allowed (read-only region editing / comments-only / tracked-changes-forced / forms-only) once the doc is open.
- Neither **encrypts** the file. Both live in plaintext XML inside the zip and can be stripped by removing the element — they are integrity/intent controls, not security. (Real encryption is the separate MS-OFFCRYPTO agile encryption at the OLE/CFB container level, out of scope here.)

```xml
</w:p>
<!-- ...1-column paragraphs of section 3... -->
<w:sectPr>                              <!-- body-level: final section (one column) -->
  <w:type w:val="continuous"/>          <!-- section 3 also begins continuous -->
  <w:pgSz .../><w:pgMar .../>
  <w:cols w:space="720"/>
  <w:docGrid w:linePitch="360"/>
</w:sectPr>
```

Key implementation trap: the `w:type="continuous"` that makes the 2-column block start mid-page lives in the **2-column section's own sectPr**, and the `continuous` that ends it lives in the **following** section's sectPr. Inserting a column block therefore means: (a) split with a new paragraph carrying the *previous* section's sectPr clone; (b) put the multi-column sectPr with `type=continuous` on the last paragraph of the block; (c) ensure the next section's sectPr also carries `type=continuous`.

## Repair tolerance — tested against Word 365 (ground truth)

Deliberately malformed variants were opened in Word 365:

| Test | Result |
|---|---|
| `w:num="3"` with only two `w:col` children (`equalWidth="0"`) | **No repair prompt.** Opened fine; `TextColumns.Count` = 3 — **`w:num` is authoritative for the count**. On resave Word synthesized a filler third child: `<w:col w:w="-1"/>`. |
| `w:col` widths + spaces summing to far less than the text width (4500 vs 9360 twips) | **No repair prompt.** Preserved byte-for-byte on resave; Word renders the columns at the declared widths (rest of the line left empty). Width mismatch is tolerated. |

Practical rule: keep `w:num` equal to the number of `w:col` children anyway (strict validators and other consumers care even if Word doesn't), and make `sum(w:w) + sum(w:space except last)` equal the text width (`pgSz@w − pgMar@left − pgMar@right`) for WYSIWYG-predictable output. Word will not punish mismatches, but it will believe `num` over the children.

# TOPIC 7 — gridBefore / gridAfter Semantics

## Schema and semantics

Both are `CT_DecimalNumber` elements (single required `w:val`) in `w:trPr`.
Schema: https://www.datypic.com/sc/ooxml/e-w_gridBefore-1.html — VERIFIED.
Semantics (ECMA-376 §17.4.14, mirror http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/gridBefore.html) — VERIFIED:

> "The number of grid columns in the parent table's table grid which shall be skipped before the contents of this table row are added to the parent table." Omitted ⇒ zero. "If this element's value is larger than the size of the table grid, then the value shall be ignored and the first cell in the row may span the full table grid."

`w:gridAfter` (§17.4.15) is the mirror image at the row end (skipped trailing grid columns) — semantics confirmed by symmetry and by ground truth below; the §17.4.15 text itself was not fetched (**UNVERIFIED as a quotation**, behavior verified empirically).

Companion widths: `w:wBefore` / `w:wAfter` (`CT_TblWidth`: `w:w` + `w:type`, normally `dxa`) state the physical width of the skipped zone. They sit in `trPr` immediately after the grid elements.

`CT_TrPr` element order (python-docx `CT_TrPr._tag_seq`, MIT, VERIFIED — identical in local fork and upstream `src/docx/oxml/table.py`):

```
w:cnfStyle, w:divId, w:gridBefore, w:gridAfter, w:wBefore, w:wAfter,
w:cantSplit, w:trHeight, w:tblHeader, w:tblCellSpacing, w:jc, w:hidden,
w:ins, w:del, w:trPrChange
```

## When Word writes them — ground truth

Dragging a row's left edge inward (COM `Row.SetLeftIndent(72pt, wdAdjustNone)` on row 2 of a 2×3 "Table Grid" table) produced this exact structure — Word **rebuilt the shared grid** to 7 columns interleaving both row layouts, then expressed each row as spans plus skip counts:

```xml
<w:tblGrid>
  <w:gridCol w:w="1440"/><w:gridCol w:w="1680"/><w:gridCol w:w="1440"/>
  <w:gridCol w:w="1680"/><w:gridCol w:w="1440"/><w:gridCol w:w="1680"/>
  <w:gridCol w:w="1440"/>
</w:tblGrid>
<w:tr>                                    <!-- row 1: occupies grid cols 1-6 -->
  <w:trPr>
    <w:gridAfter w:val="1"/>
    <w:wAfter w:w="1440" w:type="dxa"/>
  </w:trPr>
  <w:tc><w:tcPr><w:tcW w:w="3120" w:type="dxa"/><w:gridSpan w:val="2"/></w:tcPr>...</w:tc>
  <w:tc><w:tcPr><w:tcW w:w="3120" w:type="dxa"/><w:gridSpan w:val="2"/></w:tcPr>...</w:tc>
  <w:tc><w:tcPr><w:tcW w:w="3120" w:type="dxa"/><w:gridSpan w:val="2"/></w:tcPr>...</w:tc>
</w:tr>
<w:tr>                                    <!-- row 2: occupies grid cols 2-7 -->
  <w:trPr>
    <w:gridBefore w:val="1"/>
    <w:wBefore w:w="1440" w:type="dxa"/>
  </w:trPr>
  <!-- same three 2-span cells -->
</w:tr>
```

Invariant visible here (and the one to validate on write): for every row,
`gridBefore + Σ(cell gridSpans) + gridAfter = len(tblGrid)`, and `wBefore`/`wAfter` = sum of the skipped `gridCol` widths.

## Grid model translation (python-docx approach)

Upstream python-docx (MIT license, https://raw.githubusercontent.com/python-openxml/python-docx/master/src/docx/oxml/table.py) — quoted verbatim, VERIFIED:

```python
@property
def grid_offset(self) -> int:
    """Starting offset of `tc` in the layout-grid columns of its table.

    A cell in the leftmost grid-column has offset 0.
    """
    grid_before = self._tr.grid_before
    preceding_tc_grid_spans = sum(
        tc.grid_span for tc in self.xpath("./preceding-sibling::w:tc")
    )
    return grid_before + preceding_tc_grid_spans
```

with `CT_Row.grid_before` / `grid_after` returning `trPr`'s value or 0 when absent. So: **a cell's grid column = row's gridBefore + sum of gridSpans of preceding cells**. Any cell-addressing feature (merge, set-column-width, insert-column) must use this offset, never the `w:tc` index.

## Inserting / deleting a grid column that falls in a before/after zone

Derived guidance (grounded in the verified semantics + the invariant above; not itself a spec quote):

- **Insert a grid column at grid index `i`** (0-based, inserting a `w:gridCol` of width `w`):
  - Row with `gridBefore = b`: if `i < b` (new column lands inside the leading skip zone), increment `w:gridBefore` to `b+1` and add `w` to `w:wBefore@w:w`; do NOT add a `w:tc`. Create the elements if the row previously had none and `i` falls before its first cell only when you intend the new column to be skipped for that row — otherwise add a real `w:tc`.
  - If `i >= b + Σspans` (lands in the trailing skip zone), increment `w:gridAfter` and add `w` to `w:wAfter@w:w`.
  - Otherwise insert a `w:tc` (or bump a spanning cell's `gridSpan`) as usual.
- **Delete grid column `i`** (width `w`):
  - `i < b`: decrement `w:gridBefore`; subtract `w` from `w:wBefore@w:w`; when the count reaches 0 remove `w:gridBefore` and `w:wBefore` entirely (omitted = 0).
  - `i` in the trailing zone: same on `w:gridAfter`/`w:wAfter`.
  - Otherwise remove/shrink the covering `w:tc`.
- After either operation re-verify the row invariant against the updated `tblGrid`. Rows failing it render unpredictably; keep `wBefore/wAfter` equal to the summed widths of the skipped `gridCol`s (that is exactly what Word writes, per ground truth).
- Reading tolerance: per ECMA, `gridBefore` larger than the grid is ignored by consumers — clamp on read, fix on write.

Also seen in the wild (pasted/nested tables): rows whose cells were deleted at the start commonly carry `gridBefore` — treat it as routine input, not an anomaly.

# TOPIC 8 — Table Styles

## Style part basics

A table style is `w:style w:type="table" w:styleId="..."` in `word/styles.xml`. Text inside table cells resolves through the style hierarchy (ECMA-376 §17.7.2): **docDefaults → table style (its `pPr`/`rPr`/`tblPr` plus matching conditional `tblStylePr` blocks) → numbering → paragraph style → character style → direct formatting**. So a table style's `w:rPr` affects cell text only where no paragraph/character style or direct formatting overrides it. (Hierarchy per the spec section number; layering behavior cross-checked against the Microsoft "OpenXML Styles 101" article below. Marked VERIFIED for the order of table-style-below-paragraph-style, which that article demonstrates.)

Primary walkthrough source: *OpenXML Styles 101 — Understanding Table Style Conditional Formatting* (Microsoft Open Specification blog, archived): https://learn.microsoft.com/en-us/archive/blogs/openspecification/openxml-styles-101-understanding-table-style-conditional-formatting

## Conditional formatting — `w:tblStylePr`

`w:tblStylePr w:type="..."` blocks inside the style; each may contain (in order) `w:pPr`, `w:rPr`, `w:tblPr`, `w:trPr`, `w:tcPr`. Full `ST_TblStyleOverrideType` list — VERIFIED (https://www.datypic.com/sc/ooxml/t-w_ST_TblStyleOverrideType.html):

```
wholeTable, firstRow, lastRow, firstCol, lastCol,
band1Vert, band2Vert, band1Horz, band2Horz,
neCell, nwCell, seCell, swCell
```

(`band1*` = odd bands, `band2*` = even bands; `neCell` etc. are the four corner cells, named by compass point. Note nw = top-left in LTR tables.)

**Application order — Word deviates from the spec.** ECMA-376 §17.7.6.6 says columns bands before row bands; MS-OI29500 §2.1.250 documents what Office actually does (later overrides earlier):

> Whole table → **banded rows** → **banded columns** → first column, last column → first row, last row → corner cells.

(Quoted via the Styles 101 article, which cites §2.1.250 directly — VERIFIED.)

**Band sizes.** `w:tblStyleRowBandSize` / `w:tblStyleColBandSize` (in the style's `w:tblPr`) give rows/columns per band. ECMA default when omitted is 1, **but Word's default is 0, and 0 means "no banding applied"** (MS-OI29500 §2.1.251, via Styles 101 — VERIFIED). **Always write `<w:tblStyleRowBandSize w:val="1"/>` and `<w:tblStyleColBandSize w:val="1"/>` explicitly in any banded style**, or the bands silently do not render in Word.

## `w:tblLook` — gate for the conditional formats

In the table's `w:tblPr` (position: near the end of tblPr, after `w:tblCellMar`, before `w:tblCaption`; python-docx `CT_TblPr._tag_seq` places it 15th of 18). Legacy bitmask (`w:val`) — VERIFIED (multiple sources: Martin Eve https://eve.gd/2014/04/17/bitmask-values-for-wtbllook-wval-attribute-in-ooxml/, MS-OI29500 §2.1.160 https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/90f075ce-b16d-422a-b1b0-39c9777a594e, officeopenxml.com/WPtblLook.php):

| Bit | Meaning |
|---|---|
| `0x0020` | apply firstRow formatting |
| `0x0040` | apply lastRow formatting |
| `0x0080` | apply firstColumn formatting |
| `0x0100` | apply lastColumn formatting |
| `0x0200` | **no** horizontal (row) banding |
| `0x0400` | **no** vertical (column) banding |

**Current Word writes BOTH forms on one element** — ground truth, every table Word 365 created here:

```xml
<w:tblLook w:val="04A0" w:firstRow="1" w:lastRow="0" w:firstColumn="1"
           w:lastColumn="0" w:noHBand="0" w:noVBand="1"/>
```

`0x04A0 = 0x0020 | 0x0080 | 0x0400` — exactly matching the explicit attributes. Write both, kept in sync; readers should prefer the explicit attributes (ISO strict) and fall back to the bitmask. Remember the banding attributes are **negative** (`noVBand="1"` disables column banding — the most common reason column banding "doesn't work").

# TOPIC 9 — Tab Stops, Paragraph Borders, Shading, Drop Caps

## Tab stops — `w:pPr/w:tabs/w:tab`

Enums VERIFIED (https://www.datypic.com/sc/ooxml/t-w_ST_TabJc.html, https://www.datypic.com/sc/ooxml/t-w_ST_TabTlc.html):

- `@w:val` (ST_TabJc): `clear`, `left`, `center`, `right`, `decimal`, `bar`, `num`. (ISO strict adds `start`/`end` aliases for left/right; transitional Word files use `left`/`right` — ground truth confirms Word writes `center`, `right`, `decimal`.)
- `@w:pos` (ST_SignedTwipsMeasure): ECMA-376 §17.3.1.37 (mirror http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/tab_1.html): "position ... **with respect to the current page margins. Negative values are valid** and move the tab stop into the current page margin." So pos is measured from the text margin, NOT shifted by paragraph indent (`w:ind`); a left indent moves text, not the tab grid. - Entries must be sorted ascending by `w:pos`; `w:tabs` sits in pPr after `w:shd`, before `w:suppressAutoHyphens`.

```xml
    <w:rPr>
      <w:position w:val="-10"/>
      <w:sz w:val="110"/>
    </w:rPr>
    <w:t>D</w:t>
  </w:r>
</w:p>
<w:p>
  <w:r><w:t>ropped capital paragraph text follows here ...</w:t></w:r>
</w:p>
```

Anatomy of the pattern (all elements present in ground truth):

| Piece | Purpose |
|---|---|
| `w:framePr w:dropCap="drop" w:lines="3" w:wrap="around" w:vAnchor="text" w:hAnchor="text"` | the frame; `margin` instead of `drop` puts the letter in the margin. Non-zero "distance from text" adds `w:hSpace` (twips) — not exercised here, **UNVERIFIED**. |
| `w:keepNext` | keeps the letter paragraph glued to the body paragraph |
| `w:spacing w:line="805" w:lineRule="exact"` | frame line height, twips, exact rule (805 ≈ 3 body lines + leading for this font) |
| `w:textAlignment w:val="baseline"` | baseline alignment inside the frame |
| `w:position w:val="-10"` (run + pPr/rPr) | lowers the glyph 5 pt (half-point units, negative = lowered) |
| `w:sz w:val="110"` | 55 pt letter (half-points) — the enlarged cap |

The numeric values (`line`, `position`, `sz`) are font-metric-dependent; Word computes them from the body font and `lines` count. A tool writing drop caps directly should either copy these observed ratios for the document's font/size (sz ≈ lines × body line height expressed in half-points, then tune) or, on Windows, delegate to Word COM `Paragraph.DropCap` (`.Position = wdDropNormal`, `.LinesToDrop = n`), which produces exactly the XML above. Removing a drop cap must merge the two paragraphs back and strip framePr/spacing/rPr overrides.

# TOPIC 10 — Run-level Properties (lang, hidden text, spacing, caps, dstrike)

## w:lang — Languages for Run Content (ECMA-376 §17.3.2.20 / 1st ed. §2.3.2.18)

```xml
<w:rPr>
  <w:lang w:val="en-US" w:eastAsia="ko-KR" w:bidi="ar-SA"/>
</w:rPr>
```

Element type `CT_Language`, empty content, three optional attributes, each `ST_Lang` (BCP-47/RFC-3066 code) ([datypic](http://www.datypic.com/sc/ooxml/e-w_lang-1.html)):

| Attribute | Governs |
|---|---|
| `w:val` | "the language which shall be used to check spelling and grammar (if requested) when processing the contents of this run which use **Latin characters**" |
| `w:eastAsia` | "the contents of this run which use **East Asian characters, as determined by the Unicode character values**" |
| `w:bidi` | "the contents of this run which use **complex script characters, as determined by the Unicode character values**" |

**VERIFIED (spec text via [docx4java mirror](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/lang.html)):** the split is per-character by Unicode script, exactly as hypothesized. The spec's own example: `<w:lang w:val="fr-CA" w:bidi="he-IL"/>` means "any complex script contents shall be spell and grammar checked as if they were Hebrew, and any Latin character contents shall be spell and grammar checked as if they were French (Canada)." If an attribute is omitted, "the languages for the contents of this run shall be automatically determined based on their contents using any appropriate method."

**Mixed Korean+English runs:** set BOTH `w:val="en-US"` and `w:eastAsia="ko-KR"` on the same run's `w:lang`; Word routes each character to the proofing language of its script class. This is how Word itself tags runs typed on a Korean system.

**Font pairing (w:rFonts, §17.3.2.26):** the same per-script routing applies to fonts. `w:rFonts` has four slots — ascii ("all characters in the ASCII range (0–127)"), hAnsi (everything not in the other three classes), eastAsia ("all characters in an East Asian Unicode range"), cs ("all characters in a complex script Unicode range"). "The use of each of these fonts shall be determined by the Unicode character values of the run content." The `w:hint` attribute (ST_Hint) "specifies the font type which shall be used to format any **ambiguous** characters in the current run" — characters that map into multiple classes (CJK punctuation, full-width forms, etc.). Word-produced Korean text typically carries `<w:rFonts w:hint="eastAsia"/>` (often with an explicit `w:eastAsia="맑은 고딕"` slot). For a run you tag Korean, write:

```xml
<w:rPr>
  <w:rFonts w:eastAsia="Malgun Gothic" w:hint="eastAsia"/>
  <w:lang w:val="en-US" w:eastAsia="ko-KR"/>
</w:rPr>
```

Source: [rFonts spec text](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/rFonts.html).

## w:noProof (§17.3.2.21)

Empty toggle element in rPr. Spec: "the contents of this run shall not report any errors when the document is scanned for spelling and grammar"; it is "entirely at the consumer's/producer's discretion whether this is done by not checking the region ... or simply by suppressing the results." Note `noProof` suppresses BOTH spelling and grammar and beats `w:lang`; Word's UI equivalent is "Do not check spelling or grammar." ([spec text](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/noProof.html))

## Hidden text — w:vanish vs w:specVanish

- **`w:vanish`** (§17.3.2.41): "specifies whether the contents of this run shall be hidden from display at display time in a document." An application "may have settings to force hidden text to be displayed." Toggle-property semantics in styles: "setting this property shall toggle the current state" when applied through the style hierarchy; as direct formatting, true/false is absolute. ([spec text](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/vanish.html))
- **`w:specVanish`** (§17.3.2.36): "the given run shall always behave as if it is hidden, **even when hidden text is being displayed**." Its purpose is the **style separator**: applied to a paragraph mark's rPr so "a paragraph style can be applied to a part of a paragraph, and still appear in the Table of Contents" — the paragraph mark never breaks the paragraph for display. Do not use it for ordinary hidden text; Word only ever writes it on paragraph marks (Ctrl+Alt+Enter style separator). ([spec text](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/specVanish.html))

## Character spacing family

| Element | Value type | Units / meaning |
|---|---|---|
| `<w:spacing w:val="..."/>` (in rPr) | `ST_SignedTwipsMeasure`, required `w:val` | Signed **twentieths of a point**; positive expands inter-character pitch, negative condenses. (Word UI "Spacing Expanded/Condensed 1pt" = `w:val="20"`.) [datypic](http://www.datypic.com/sc/ooxml/e-w_spacing-2.html) |
| `<w:kern w:val="..."/>` | `ST_HpsMeasure` | **Half-points**. "The smallest font size which shall have its kerning automatically adjusted"; "if the font size in the sz element is smaller than this value, then no font kerning shall be performed." Absent through the whole hierarchy = no kerning. Word writes `w:val="0"` to mean kerning off (0-behavior not addressed by spec — treat 0 as disabled). [spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/kern.html) |
| `<w:position w:val="..."/>` | `ST_SignedHpsMeasure` | **Half-points**, signed: "If the val attribute is positive, then the parent run shall be raised above the baseline ... If negative ... lowered below the baseline." Distinct from `w:vertAlign` (super/subscript), which also shrinks the font. [spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/position.html) |
| `<w:w w:val="..."/>` | `ST_TextScale` | Per-character horizontal scaling: "the percentage by which the contents of this run shall be expanded or compressed with respect to its normal (100%) character width." Omitted = 100%. `ST_TextScale` is an integer restricted to **0–600** inclusive ([datypic](http://www.datypic.com/sc/ooxml/t-w_ST_TextScale.html), [spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/w_1.html)). Distinct from `w:spacing`, which "adds pitch without altering actual character dimensions." |

## smallCaps / caps and strike / dstrike — mutual exclusivity (VERIFIED)

- `w:caps` (§17.3.2.5): "Any lowercase characters in this text run shall be formatted for display only as their capital letter character equivalents" — display-only, "does not change the Unicode character for lowercase text." **"This element shall not be present with the smallCaps (§2.3.2.31) property on the same run, since they are mutually exclusive in terms of appearance."** ([caps](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/caps.html))
- `w:smallCaps` (§17.3.2.33): mirror-image sentence: "shall not be present with the caps (§2.3.2.4) property on the same run." ([smallCaps](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/smallCaps.html))
- `w:dstrike` (§17.3.2.9): **"This element shall not be present with the strike (§2.3.2.35) property on the same run, since they are mutually exclusive in terms of appearance."** ([dstrike](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/dstrike.html))
- What Word does if both are present anyway: not specified; Word's UI treats each pair as radio buttons and clears the other. **UNVERIFIED** which wins on load if a producer writes both — implementation should simply never emit both, and when setting one, remove the other.

# TOPIC 11 — Moving an Outline Section Block

## Block model (confirmed)

Section-to-move = the heading paragraph + all following **body-level siblings** (`w:p` AND `w:tbl`, in document order) up to but excluding the next paragraph whose effective outline level (pPr `w:outlineLvl` or its style's) is same-or-higher (numerically lower-or-equal). This matches Word's own "select heading + collapse/move" behavior and Open-Xml-PowerTools' Source model of contiguous body-level content runs. Two subtleties:

- Outline level comes from the **style chain** (Heading1 style carries `<w:outlineLvl w:val="0"/>`), with direct pPr overriding; resolve via style inheritance, not just direct formatting.
- Tables never carry a heading; they always belong to the preceding heading's block. A table as the FIRST body element after the moved block's insertion point must not merge with a table at the end of the moved block (Word joins adjacent tables); insert an empty paragraph guard if both boundaries are tables.

## Gotchas when relocating the block

**(a) Bookmarks straddling the boundary.** `bookmarkStart`/`bookmarkEnd` are independent milestone elements matched by `w:id`; they can legally sit at body level between paragraphs, and a pair may straddle your block edge. ECMA-376 on the orphan-end case: "If no bookmarkStart element exists prior to this element in document order with a matching id attribute value, then this element is ignored and no bookmark is present in the document with this name" ([bookmarkEnd spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/bookmarkEnd.html)). So an orphaned END is spec-tolerated (bookmark silently ceases to exist). The reverse (start with no end) is not addressed by the spec; in practice Word tolerates it without a repair prompt and drops/normalizes the bookmark on next save — **UNVERIFIED** against documentation, but note that a MOVE within the same body never orphans anything permanently: the pair still exists in document order, it just may now be inverted (end before start), which kills the bookmark. Correct handling: after the move, for each id whose start/end ordering inverted, either move the stray marker to hug the block edge or delete the pair. Cross-reference REF fields pointing at a deleted/dead bookmark show "Error! Reference source not found." on next field update — that is the user-visible failure, not repair.

**(b) Field ranges (the hard constraint).** Complex fields are delimited by `<w:fldChar w:fldCharType="begin"/>` ... `separate` ... `end` runs and MAY span paragraphs (TOC fields always do). Spec: "A complex field is defined via the use of the two required complex field characters ... If a complex field is not closed before the end of a document story, then no field shall be generated and each individual run shall be processed as if the field characters did not exist" — i.e., a begin without end degrades to literal text, and a moved block that carries an `end` without its `begin` corrupts the *remaining* field structure ([fldChar spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/fldChar.html)). **Never split a field range.** Detect open state by scanning runs across the candidate block in document order with a depth counter: `begin` => depth+1, `end` => depth-1 (fields nest, e.g. IF containing REF). The block is safe iff the counter starts and ends at 0 and never goes negative inside it. If a heading boundary lands mid-field, extend the block to the field's end (or refuse the move). `w:fldSimple` is a normal container element and moves atomically — no issue.

**(c) `w:sectPr` inside the moved block.** Section properties for every section except the last live in the **pPr of the section's last paragraph**: "For all sections except the final section, the sectPr element is stored as a child element of the last paragraph in the section. For the final section, this information is stored as the last child element of the body element" ([sectPr spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/sectPr_2.html), [sectPr_3](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/sectPr_3.html)). Consequences: a paragraph inside your block carrying pPr/sectPr IS a section break — moving it moves the break, and everything formerly governed by that sectPr (headers/footers via rel ids, page size, margins, numbering restart) is re-scoped to the content now preceding its new position, while the content at the old location falls under the NEXT sectPr in document order. If the moved block is the tail of the document, the body-level trailing sectPr must remain the last child of `w:body` — never pull it into the block. Safe policy: detect pPr/sectPr in the block; either (i) leave the sectPr behind by transplanting it to the paragraph now preceding the block's original position, or (ii) move it knowingly (user asked to move the whole section including its break). Also: Open-Xml-PowerTools refuses documents containing `w:sectPrChange` outright ("contains section changes (w:sectPrChange), not supported" — DocumentBuilder.cs line ~1410), a sensible guard to copy.

**(d) Comments.** `commentRangeStart`/`commentRangeEnd` (matched by `w:id`) plus the `w:commentReference` run element that anchors the comment to `comments.xml`. Same straddle logic as bookmarks; additionally, a range without its `commentReference` run (or vice versa) leaves a dangling comment. Word is tolerant of an unmatched commentRangeStart/End (the highlight range collapses to the reference mark) but a `commentReference` whose id is missing from comments.xml is a repair risk. Keep all three pieces together; OXPT's fixup (below) re-adds the missing end AND fabricates the reference run.

**(e) Numbering continuity.** List numbering is computed from **document order** of paragraphs sharing a `numId`. Moving list paragraphs does not restart anything by itself — the sequence simply recounts in the new order, which can look like a restart/renumber (e.g., items 4-6 moved above items 1-3 become 1-3). Restart semantics live in numbering.xml (`w:lvlOverride`/`w:startOverride` on the num, or `w:lvlRestart` on the level), not in body content, so a pure body move never breaks XML validity — the risk is purely visual/semantic. Flag when the moved block contains partial pieces of a numbered list (some-but-not-all paragraphs of one numId run).

**(f) `w:permStart`/`w:permEnd`** (range editing permissions): same milestone pattern, matched by `w:id`. Straddling produces an unprotected/misprotected region rather than corruption; treat like bookmarks. OXPT fixes these up identically.

## What triggers Word's repair prompt vs silent tolerance

Documented hard failures (repair or refuse-to-load): schema-invalid document.xml; `wp:docPr/@id` of 0 or > 2147483646 (see Topic 4); broken `xsi:type` on dcterms dates in core.xml (community-verified, Topic 4). Spec-tolerated (silent): unmatched bookmarkEnd ("ignored" per spec), unclosed field (degrades to literal text per spec), orphan permStart/End. In practice moves WITHIN one body that keep every `w:p`/`w:tbl` intact and don't split a field almost never trigger repair; the failure mode is semantic (dead bookmarks, wrong section formatting, comment ranges collapsed). **UNVERIFIED as a general claim** — Word's repair triggers are not exhaustively documented anywhere; the above is spec text plus the OXPT authors' defensive-coding choices.

## Open-Xml-PowerTools DocumentBuilder (MIT license — usable freely)

Repo: https://github.com/OpenXmlDev/Open-Xml-PowerTools — license is **MIT** (Copyright Microsoft 2012-2017, Eric White Inc 2018-2021, Thomas Barnekow 2016-2021; verified from LICENSE file). DocumentBuilder splits/recombines documents from paragraph ranges and handles exactly the straddle problems, in `DocumentBuilder.cs`:

- **`FixRanges`** (line ~3756) runs `FixRange` for `commentRangeStart/End` (also re-adding the `commentReference` run), `bookmarkStart/End`, `permStart/End`, `moveFromRangeStart/End`, `moveToRangeStart/End`. `FixRange` scans the extracted content: for every start whose end fell outside the range it **copies the matching end from the source document and appends it at the end of the extracted content** (after the last paragraph's pPr); for every end missing its start it prepends the start at the beginning. So OXPT *closes* straddling ranges at the block boundary rather than dropping them.
- **`DeleteUnmatchedRange`** then deletes `moveFrom`/`moveTo` (tracked-move) ranges whose counterpart is absent — move ranges, unlike bookmarks, are deleted rather than closed.
- **`AdjustUniqueIds`** (line ~2028) remaps every bookmark id in incoming content above the target's current max id (colliding bookmark IDs across merged parts), and **renumbers ALL `wp:docPr` ids sequentially across main document, headers, footers, footnotes, endnotes** — evidence that docPr id uniqueness is treated as document-wide.
- Section handling: `KeepSections` logic hoists a trailing paragraph-level sectPr to body level when it ends the output ("last-body-sectPr stays last", lines ~319-323), strips sectPr from mid-content when sections are not kept (line ~2125), and back-fills headers/footers on sectPr elements that lack them **from the following section** (line ~488) so per-chapter headers survive.
- **Notably absent: any `fldChar` handling.** DocumentBuilder contains zero field fixup — it relies on callers choosing paragraph boundaries that don't split fields. Your tool must implement the depth-counter scan itself.

# TOPIC 12 — Style / Template Transfer

## Parts that matter, in priority order

1. **`word/styles.xml`** — including **`w:docDefaults`** (document-wide default rPr/pPr that every style inherits; forgetting it is the #1 reason a transfer "doesn't take") and `w:latentStyles` (UI visibility/priority of built-ins, cosmetic but affects the Styles pane).
2. **`word/theme/theme1.xml`** — theme fonts (`majorHAnsi`/`minorHAnsi`/`majorEastAsia`/`minorEastAsia`) and colors. styles.xml routinely references fonts as `w:asciiTheme="minorHAnsi"` etc.; without the theme those resolve against the wrong font scheme.
3. **`word/settings.xml`** — only some children matter for appearance: `w:compat` (layout compatibility switches; different compat = different line breaking), `w:defaultTabStop`, `w:evenAndOddHeaders`, `w:themeFontLang`, `w:characterSpacingControl`, `w:autoHyphenation` family, `w:clrSchemeMapping`. Never copy `w:rsids`, `w:proofState`, `w:attachedTemplate`, or `w:documentProtection` wholesale from another doc.
4. **`word/fontTable.xml`** — font substitution metadata (panose, charset). Low risk, copy along with styles.
5. **`word/numbering.xml`** — list definitions. Critical coupling: paragraph styles reference numbering via `style/pPr/numPr/numId`, and numbering references styles back via `abstractNum/lvl/pStyle`, `abstractNum/numStyleLink`, `abstractNum/styleLink` (this bidirectional coupling is exactly the relationship list OXPT encodes in its expected-relationships table, DocumentBuilder.cs lines ~750-800).
6. Page geometry is NOT in styles.xml — margins/page size/headers live in the body's `sectPr` (+ header/footer parts). A full "make it look like B" also means copying B's sectPr attributes onto A's sections.

## Risks of a wholesale styles.xml swap

- **Dangling `pStyle`/`rStyle`/`tblStyle`**: body references a styleId absent from the new styles.xml. **VERIFIED spec behavior — silent fallback, not repair:** "If this element is omitted, **or it references a style which does not exist**, then no paragraph style shall be applied to the current paragraph" (pStyle, [spec](http://webapp.docx4java.org/OnlineDemo/ecma376/WordML/pStyle_1.html)) — i.e., the paragraph renders with docDefaults/Normal. No repair prompt, but headings silently lose outline level, TOC breaks, navigation pane empties. Same rule pattern for rStyle/tblStyle.
- **styleId vs style name**: Word matches styles across documents **by name** (`w:name/@w:val`), but XML references use **styleId**, and the same "Heading 1" can be `Heading1` in one file and `1` or `Ttulo1` (localized producer) in another. Transfer by name-mapping, not by id string equality.
- **numId dangling**: a copied style (or body paragraph) whose `numPr/numId` points into a numbering.xml that wasn't copied/merged loses its bullets/numbers silently.
- **Theme divergence**: copied styles using `asciiTheme` refs against the old theme change fonts.
- **latentStyles count/`w:defLockedState` etc.** are harmless to swap but keep them consistent with the copied styles.xml.

## How pandoc's reference-doc works (VERIFIED from source; pandoc is GPL-2.0-or-later)

Manual ([pandoc.org/MANUAL.html](https://pandoc.org/MANUAL.html), `--reference-doc`): "The contents of the reference docx are ignored, but its stylesheets and document properties (including margins, page size, header, and footer) are used in the new docx." Pandoc writes its own document.xml against a fixed vocabulary of style **names**: paragraph styles Normal, Body Text, First Paragraph, Compact, Title, Subtitle, Author, Date, Abstract, AbstractTitle, Bibliography, Heading 1–9, Block Text, Footnote Block Text, Source Code, Footnote Text, Definition Term, Definition, Caption, Table Caption, Image Caption, Figure, Captioned Figure, TOC Heading; character styles Default Paragraph Font, Verbatim Char, Footnote Reference, Hyperlink, Section Number; table style Table.

From `src/Text/Pandoc/Writers/Docx.hs` (https://github.com/jgm/pandoc/blob/main/src/Text/Pandoc/Writers/Docx.hs, license GPL — **do not vendor code, only imitate the approach**):

- `word/styles.xml` is parsed **from the reference archive** (fallback: pandoc's bundled default docx) and pandoc *appends* any styles it needs that are missing (`newParaPropToOpenXml` creates them `basedOn BodyText` with the styleId = name minus spaces).
- `word/theme/theme1.xml`, `word/fontTable.xml` (+ fontTable rels + embedded `word/fonts/`), `word/webSettings.xml`, `docProps/app.xml`, header/footer parts and `word/media/` are copied **wholesale from the reference archive** (`collectReferenceEntries`).
- `word/settings.xml` is deliberately NOT taken wholesale: base file comes from the **dist** (default) archive "because Word sometimes adds references to footnotes or endnotes we don't have," then `copyChildren` merges an explicit allowlist of ~90 child elements from the reference (`settingsElementNames`: includes `compat`, `defaultTabStop`, `evenAndOddHeaders`, `themeFontLang`, `characterSpacingControl`, `autoHyphenation`, `clrSchemeMapping`, `docVars`, ... — and **explicitly excludes `footnotePr`/`endnotePr`** with a comment citing pandoc issue #9522). This is the strongest precedent for merge-don't-replace on settings.
- Page geometry: `extractPageLayout` reads the reference's document.xml `sectPr` and applies it to the generated body.
- numbering.xml is built fresh, with pandoc's own lists allocated from `baseListId = 1000` upward to avoid colliding with numbering copied from the reference.

## docx4j

docx4j's `MergeDocx`/enhanced DocumentBuilder is a **commercial** add-on (Plutext); the open docx4j core offers style aggregation via each part's `StyleDefinitionsPart` and the same name-based reasoning but no turnkey reference-doc transfer. Not load-bearing here. **UNVERIFIED beyond general project knowledge.**

## SAFE ALGORITHM (recommendation)

1. Snapshot from target A: set of styleIds referenced in body/headers/footers/footnotes (`pStyle`, `rStyle`, `tblStyle`, plus `numPr/numId` pairs), and A's current styles.xml id→name map.
2. Copy from reference B **wholesale**: `styles.xml` (with docDefaults + latentStyles), `theme/theme1.xml`, `fontTable.xml` (+ its rels/embedded fonts if present).
3. **Merge, never replace, `settings.xml`**: keep A's file, overwrite/insert only the pandoc allowlist subset you care about — at minimum `compat`, `defaultTabStop`, `evenAndOddHeaders`, `themeFontLang`, `characterSpacingControl`; skip `footnotePr`/`endnotePr`, `rsids`, `proofState`, `documentProtection`, `attachedTemplate`.
4. Numbering: EITHER keep A's numbering.xml untouched (safest when only prose styling should change) OR union: copy B's abstractNum/num entries, remapping `numId`/`abstractNumId` above A's max (OXPT pattern), and rewrite the copied styles' `numPr/numId` and `numStyleLink`/`styleLink`/`lvl/pStyle` references accordingly.
5. Reconcile body references: for every styleId from step 1 missing from the new styles.xml, first try **map-by-name** (A's old id→name, then B's name→id — handles Heading1 vs 1 vs localized ids), rewriting `pStyle`/`rStyle`/`tblStyle` in place; anything still unmatched, either strip the reference (spec-safe: silent fallback to Normal) or clone the old style definition into the new styles.xml as a custom style. Headings deserve the clone/map path, never the strip path, or outline structure dies.
6. Optionally copy B's `sectPr` page geometry (pgSz, pgMar, cols, titlePg) onto A's sections, keeping A's header/footer rel ids unless headers are also being transferred (then copy header/footer parts + rels + their media like pandoc does).
7. Validate: re-scan for dangling styleIds and numIds; confirm the trailing body sectPr is still the last child of `w:body`.

# TOPIC 13 — Image Alt Text + Core/App Property Writing

## Alt text: `wp:docPr` on `wp:inline` / `wp:anchor`

`wp:docPr` (type `a:CT_NonVisualDrawingProps`): attributes `id` (**required**, `a:ST_DrawingElementId` = xsd:unsignedInt), `name` (required in 1st ed.), `descr` (optional string — **this is the alt-text description** Word's "Alt Text" pane edits), `hidden`, and — added in later ISO 29500 editions and written by current Word — `title` (the pre-2016 "Title" field; modern Word UI only surfaces `descr`). datypic's 1st-edition page shows no `title` attribute ([datypic](http://www.datypic.com/sc/ooxml/e-wp_docPr-1.html)); its presence in later editions is **VERIFIED via the OOXML transitional schema/SDK** (`NonVisualDrawingProperties.Title`). Children: `a:hlinkClick?`, `a:hlinkHover?`, `a:extLst?`.

```xml
<wp:inline ...>
  <wp:extent cx="..." cy="..."/>
  <wp:docPr id="7" name="Picture 7" descr="Chart of alliance cohesion, 1977-1979" title="Figure 3"/>
  ...
</wp:inline>
```

**id uniqueness:** Microsoft's implementer notes ([MS-OI29500 §20.4.2.5](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/e7d7aeab-16eb-4963-9338-39953b8fee37)) — VERIFIED verbatim: "Word will fail to load a file if the id attribute is a value of 0" and "Word will fail to load a file if the id attribute is a value is greater than 2147483646." So the practical range is 1–2147483646. **Duplicate** ids: not covered by the implementer notes; Word generally opens such files without a repair prompt but behaviors keyed to the id (alt text association, cross-part references) can misfire — Open-Xml-PowerTools defensively renumbers every docPr in every part after any merge (AdjustUniqueIds). Recommendation: always allocate max(existing)+1 per document. Repair-on-duplicate is **UNVERIFIED**.

**python-docx access:** no public alt-text API. `document.inline_shapes[i]` → `InlineShape` wraps `wp:inline` as `._inline`; `CT_Inline.docPr` is a mapped `OneAndOnlyOne("wp:docPr")` returning `CT_NonVisualDrawingProps` (verified in [src/docx/oxml/shape.py](https://github.com/python-openxml/python-docx/blob/master/src/docx/oxml/shape.py) and [shape.py](https://github.com/python-openxml/python-docx/blob/master/src/docx/shape.py)). So:

```python
dp = shape._inline.docPr           # CT_NonVisualDrawingProps
dp.set('descr', 'alt text here')   # or dp.get('descr')
dp.set('title', 'caption title')
```

Floating shapes (`wp:anchor`) are not exposed by `inline_shapes` at all — reach them via `document.element.xpath('//wp:anchor/wp:docPr')` with lxml.

**Decorative flag (modern Word):** stored as an extension in `docPr/a:extLst`:

```xml
<wp:docPr id="7" name="Picture 7" descr="">
  <a:extLst xmlns:a="http://schemas.openxmlformats.org/drawingml/2006/main">
    <a:ext uri="{C183D7F6-B498-43B3-948B-1728B52AA6E4}">
      <adec:decorative xmlns:adec="http://schemas.microsoft.com/office/drawing/2017/decorative" val="1"/>
    </a:ext>
  </a:extLst>
</wp:docPr>
```

Namespace `http://schemas.microsoft.com/office/drawing/2017/decorative`, qualified name `adec:decorative`, Office 2019+ — VERIFIED via the Open XML SDK [Decorative class](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.office2019.drawing.decorative?view=openxml-3.0.1) ("When the object is serialized out as xml, it's qualified name is adec:decorative", `Val` attribute). The ext URI GUID `{C183D7F6-B498-43B3-948B-1728B52AA6E4}` is cross-verified across XlsxWriter, ExcelJS and LibreOffice's implementation ([LibreOffice commit tdf#143311](https://cgit.freedesktop.org/libreoffice/core/commit/?id=31084ebb59093be7dfe5ab53a20fdb3bcfde34b6)). When decorative val="1", Word ignores/clears descr.

## Core properties — docProps/core.xml (WRITING)

Root and namespaces (OPC part, ECMA-376 Part 2):

```xml
<cp:coreProperties
    xmlns:cp="http://schemas.openxmlformats.org/package/2006/metadata/core-properties"
    xmlns:dc="http://purl.org/dc/elements/1.1/"
    xmlns:dcterms="http://purl.org/dc/terms/"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <dc:title>...</dc:title>
  <dc:subject>...</dc:subject>
  <dc:creator>...</dc:creator>
  <cp:keywords>...</cp:keywords>
  <dc:description>...</dc:description>
  <cp:lastModifiedBy>...</cp:lastModifiedBy>
  <cp:revision>2</cp:revision>
  <dcterms:created xsi:type="dcterms:W3CDTF">2026-08-27T12:00:00Z</dcterms:created>
  <dcterms:modified xsi:type="dcterms:W3CDTF">2026-08-27T12:00:00Z</dcterms:modified>
</cp:coreProperties>
```

- **`xsi:type="dcterms:W3CDTF"` is REQUIRED on `dcterms:created`/`dcterms:modified`** — VERIFIED three ways: the OPC schema, python-docx's own writer ("These two require an explicit xsi:type='dcterms:W3CDTF' attribute", [oxml/coreprops.py](https://github.com/python-openxml/python-docx/blob/master/src/docx/oxml/coreprops.py), which also hacks the xsi namespace declaration onto the ROOT element — lxml would otherwise declare it on each child, which Word dislikes), and community bug reports where a malformed/missing xsi:type produced docx files that Word 2010–2019 refuses/repairs ([python-docx-template #471](https://github.com/elapouya/python-docx-template/issues/471), [Open-XML-SDK #6](https://github.com/OfficeDev/Open-XML-SDK/issues/6) — mono emitted bad date text and Word flagged the file). Word tolerance of a fully ABSENT xsi:type attribute (vs malformed value): repair is the reported outcome, but an authoritative statement is **UNVERIFIED** — always write it.
- Format: W3CDTF, `2026-08-27T12:00:00Z` (python-docx emits exactly `%Y-%m-%dT%H:%M:%SZ`, converting to UTC).
- python-docx also enforces a 255-char limit per string property (matches Word behavior).

**python-docx `core_properties` API coverage** (verified from [opc/coreprops.py](https://github.com/python-openxml/python-docx/blob/master/src/docx/opc/coreprops.py)): `author` (dc:creator), `category`, `comments` (dc:description), `content_status`, `created`, `identifier`, `keywords`, `language`, `last_modified_by`, `last_printed`, `modified`, `revision` (int), `subject`, `title`, `version` — all read/write. NOT covered: contentType, anything in app.xml or custom.xml.

## Extended properties — docProps/app.xml

Root `<Properties xmlns="http://schemas.openxmlformats.org/officeDocument/2006/extended-properties" xmlns:vt="...docPropsVTypes">`. Relevant children: `Application` (e.g. `Microsoft Office Word`), `AppVersion`, `Pages`, `Words`, `Characters`, `Company`, `TotalTime`, etc. **AppVersion format — VERIFIED conformance rule** (ECMA-376 §22.2.2.1, surfaced via [Open XML SDK ApplicationVersion docs](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.extendedproperties.applicationversion?view=openxml-3.0.1)): "The content of this element shall be of the form XX.YYYY where X and Y represent numerical values, or the document shall be considered non-conformant." Current Word writes `16.0000`. Whether Word actually raises the repair dialog on a malformed AppVersion (vs silently ignoring/regenerating app.xml): **UNVERIFIED** — reports exist both ways; the safe move is to write `16.0000` and never emit a bare `16.0` or empty element. app.xml is optional as a part; omitting it entirely is safer than writing a malformed one.

## (c) Readability and proofing

**`Document.ReadabilityStatistics`** / `Range.ReadabilityStatistics` ([word.document.readabilitystatistics](https://learn.microsoft.com/en-us/office/vba/api/word.document.readabilitystatistics)) returns the ReadabilityStatistics collection; per the [collection docs](https://learn.microsoft.com/en-us/office/vba/api/word.readabilitystatistics), indexable 1-based and "ordered as follows: **Words, Characters, Paragraphs, Sentences, Sentences per Paragraph, Words per Sentence, Characters per Word, Passive Sentences, Flesch Reading Ease, Flesch-Kincaid Grade Level**" (10 statistics; each item has `.Name`/`.Value`). VBA access does NOT require the "Show readability statistics" checkbox (that option only controls the dialog after a manual spell check) — behavior is consistent in practice but **UNVERIFIED in the docs**, which say nothing about the option.

**`Range.SpellingErrors`** ([word.range.spellingerrors](https://learn.microsoft.com/en-us/office/vba/api/word.range.spellingerrors)) returns **ProofreadingErrors**, "the words identified as spelling errors"; **`Range.GrammaticalErrors`** ([word.range.grammaticalerrors](https://learn.microsoft.com/en-us/office/vba/api/word.range.grammaticalerrors)) returns ProofreadingErrors of "the sentences that failed the grammar check" ("There can be more than one error per sentence"; Count=0 when clean). **Each item is a Range** — get flagged text via `err.Text` and context via `err.Sentences(1).Text` (a spelling error is a word-level Range, so its first Sentence is the containing sentence) or by expanding a Duplicate of the range (`dup.Expand(Unit=3)` wdSentence — expand a copy, not the error range itself).

Performance on a 150+ page document: first access to `Document.Content.SpellingErrors.Count` forces Word to proof the whole story synchronously (seconds to minutes; **UNVERIFIED in docs**, well-established in practice). Recommendations:
- `app.Options.CheckGrammarWithSpelling = True` ([word.options.checkgrammarwithspelling](https://learn.microsoft.com/en-us/office/vba/api/word.options.checkgrammarwithspelling)) so one pass gathers both; note the docs steer VBA users to `CheckSpelling`/`CheckGrammar` methods for interactive checks — for enumeration you want the collections, not the dialogs.
- Iterate per chunk: walk `doc.Paragraphs` in blocks (or per `Range` chapter slices) and read each sub-Range's `.SpellingErrors`, yielding progress instead of one monolithic pass.
- `app.ScreenUpdating = False`, `app.Visible = False`, and consider `doc.ShowSpellingErrors = False` during the pass to skip squiggle rendering.
- Language correctness depends on the run-level `w:lang` tagging from Topic 1; `err.LanguageID` tells you which proofing language flagged it.

## (d) `Range.InsertFile` and merging dissertation chapters

**Signature** ([word.range.insertfile](https://learn.microsoft.com/en-us/office/vba/api/word.range.insertfile)):

```
Range.InsertFile(FileName As String [required], Range, ConfirmConversions, Link, Attachment)
```

`Range` (Variant): when the inserted file is a Word document this names a **bookmark** in the source (insert only that bookmark's content); `ConfirmConversions` prompts on non-Word formats; `Link:=True` inserts an INCLUDETEXT field instead of static text; `Attachment` is for email use.

**Style collision behavior:** when a styleId/name in the incoming file already exists in the destination, the incoming text is re-rendered with the **destination's** definition of that style (same rule as Insert > Object > Text from File; Microsoft's merge guidance warns "The format might not stay the same when you merge documents" — [How to merge Word documents](https://learn.microsoft.com/en-us/office/troubleshoot/word/merge-word-documents)). Corroborated by third-party documentation of the same behavior (destination styles take precedence, e.g. [e-iceblue merge guide](https://www.e-iceblue.com/en/doc/how-to-merge-word-documents.html)); direction of precedence is **not stated in the InsertFile doc itself** — treat as VERIFIED-by-convergence. Styles that exist only in the source ARE copied into the destination.

**Section breaks:** section breaks *inside* the source come along with the content, but the source's **final section properties live in its trailing body-level sectPr**, which travels with the last paragraph mark — and Word does not apply that final sectPr's header/footer/page setup to the insertion context unless a section boundary isolates it. Hence chapters inserted back-to-back into one section inherit the destination section's headers/footers and page numbering, and per-chapter headers vanish.

**Best practice for chapter merging (per-chapter headers/footers/page numbering preserved):**

```python
rng = doc.Content
rng.Collapse(0)                                   # wdCollapseEnd = 0
for chapter in chapters[1:]:
    rng.InsertBreak(2)                            # wdSectionBreakNextPage = 2 (WdBreakType)
    rng.Collapse(0)
    rng.InsertFile(FileName=chapter)
    rng = doc.Content; rng.Collapse(0)
```

Insert the `wdSectionBreakNextPage=2` break **BEFORE** each InsertFile ([WdBreakType](https://learn.microsoft.com/en-us/office/vba/api/word.wdbreaktype): NextPage=2, Continuous=3, EvenPage=4, OddPage=5, wdPageBreak=7), then immediately set the new section's `HeaderFooter.LinkToPrevious = False` and `PageSetup` before/after inserting, so each chapter owns a section whose headers don't chain back. Restart numbering per chapter via `section.Footers(wdHeaderFooterPrimary).PageNumbers.RestartNumberingAtSection = True`. Fields inside inserted chapters (cross-refs, TOC) need a final `doc.Fields.Update()`.

**Alternative without COM:** Open-Xml-PowerTools DocumentBuilder (MIT) with `Source(..., KeepSections: true)` per chapter does the same job losslessly — it keeps each chapter's sectPr, back-fills missing headers/footers from the following section, renumbers bookmark/docPr ids, merges styles by name, and remaps numbering ids (Topic 2). For a Python MCP server, porting its FixRanges + AdjustUniqueIds + KeepSections logic to lxml is the recommended non-COM path.
